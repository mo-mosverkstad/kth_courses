## Requirement check

| Requirement | Where in the model |
|---|---|
| Course layout: code, name, HP, min/max students | `course`, versioned `course_layout` |
| Course instance: ID, period, year, students | `course_instance`, `academic_period`, `period` |
| Extensible teaching activities with multiplication factor | `teaching_activity` |
| Planned hours per activity, derived exam/admin hours | `planned_activity`, `derived_activity_formula` |
| Departments with a manager who is an employee | `department.manager_employee_id` (deferred FK) |
| Employees: department, skills, contact details, salary, job title, supervisor | `employee`, `employee_skill`, `person_address`, `person_phone_number`, `employee_salary`, `job_title`, `supervisor_id` |
| Many-to-many allocations with hours | `teaching_allocation` |
| Max 4 course instances per period | `allocation_rule.max_courses` + note |
| Higher grade: all data in the database | factors, formula constants, max-4 rule and period dates are stored |
| Higher grade: versioning | `course_layout.version`, salary history by `valid_from` |

Against the assessment criteria:
- crow's foot cardinalities are correct
- the model is in 3NF
- naming is consistent (`id` for PKs, `<table>_id` or a role name for FKs)
- constants live in tables (`period`)
- derived data is computed rather than stored
- rules that aren't visible in the diagram are explained in notes

**For the Discussion chapter:**
- **Free-text properties:** `address_property` and `phone_number_property` are free text. The criteria prefer lookup tables for constants, so explain the choice.
- **Fixed formula inputs:** the formula table only supports students and HP as inputs.
- **What isn't versioned:** factors, formulas and `course_name` have no version history.
- **Report topics:** the two required higher-grade discussions, storing all data in the database and keeping multiple versions.
