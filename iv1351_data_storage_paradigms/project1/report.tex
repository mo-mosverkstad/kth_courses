\section{Introduction}

% \textbf{This chapter tells \textit{what} are you going to do.} 
% Explain the task and the requirements on the solution. It's important to clearly state the requirements. \textit{Also specify which other student you worked with when solving the tasks, or if you worked alone.}

This report concerns the design of a course database system. The database system stores courses, course layout versions, teaching allocations, and employees at a university. A conceptual diagram, along with a logical-physical ER-diagram is created for modeling the database and specifying the database schema/layout, as well as queries for creating the database tables, inserting sample table data, and additional database trigger operations for complying with requirement constraints. Additionally, the project task is carried out alone.

The database is intended to store university courses and employees (teachers), which are described as below. The purpose is to generate reports and statistics from the given data, for instance calculating the total teaching cost of a course instance in a given time interval.

The course database requirements can be divided into different parts, each with their constraints:

\subsection{Course layout, instances and activities}
The first part concerns course layout and course instances. For each course, a unique course code is assigned, while the course name, ECTS credits (högskolepoäng or hp), the minimum and maximum number of students are also specified in the course layout. A course instance is a particular instance with its layout, given in a specified academic year. The academic year and study/academic period, labelled as P1, P2, P3, and P4, and the number of students in the instance, are specified in the course instance.

Each course instance contain a number of teaching activities, labelled as lecture, lab, tutorial, seminar, examination, administration and other. More teaching activity types could be added into the database, such as help sessions. The total number of required hours for each teaching activity is calculated differently.
For some teaching activities, such as lecture, lab, tutorial and seminar, the number of required hours can be calculated by multiplying the number planned hours with a multiplication factor of a given teaching activity. In other words, if the multiplication factor for lecture is 5, that means for every hour of holding lecture, 5 hours are required including preparation time.
For other teaching activities, the number of required hours are derived from the number of students or ECTS credits. The formulae for calculating the required hours of examination and admin are stated as below (taken from project description):

\begin{lstlisting}
Examination hour = 32 + 0.725 * #Students
Admin hours = 2 * HP + 28 + 0.2 * #Students
\end{lstlisting}

\subsection{Departments, people and employees}
The university has a number of employees (or teachers), with their contact details, job title and salary recorded in the database. The salary format can be given monthly. Employee salaries can be changed, thus it is necessary to version them. Employees are affiliated with different departments and are allocated to different teaching activities of course instances. Allocations can be proceeded depending on the given skill set of employees. The university contains multiple departments, each with a manager who is also an employee. Each employee can also have a supervisor, which is also another employee.

Employees can be allocated to different course instances, while a course instance can have multiple employees being allocated in. However, one teacher must not be allocated more than 4 different course instance in a same academic period.

\subsection{Relational database model}

The relational database model organizes data into relations (tables). Each relation (table) consists of rows (tuple or records) and columns (attributes). A relation has both an intentional state, which is the same as domain definition, and an extensional state, which describes the current data currently being stored in the table. A table can be considered as a relation, since each tuple exists in the table domain, which is a cross product of the domains of individual attributes.

The relational algebra and relational calculus provides different relation (table) operations, such as selecting tuples and projecting attributes of a relation. Additionally, it also states that relationships between tables can be established using primary and foreign keys, and can be considered by an equijoin between the two tables. A primary key uniquely identifies each record in a table, while a foreign key references a record in another table and maintains referential integrity.

The relational database model is an important key concept in terms of organizing the given data in terms of courses and employees since the database contains multiple interconnected entities, such as courses, course instances, employees, departments, and teaching activities.

\subsection{SQL}
Structured Query Language (SQL) is used to define, manipulate, query, and retrieve data in relational databases. Instead of specifying the query in relational calculus which looks mathematically verbose, SQL offers a query specification that resembles natural language. The language include multiple parts, such as Data Definition Language (DDL) which is used to create and alter database table schema, Data Query Language (DQL) which is used to retrieve data from tables using \texttt{SELECT} and Data Manipulation Language (DML) which is used to \texttt{INSERT}, \texttt{UPDATE} and \texttt{DELETE} records.

During creating database tables, database constraints on tables are used to further restrict the domain. The constraints includes for instance primary key constraints, foreign key constraints that specify actions during \texttt{ON UPDATE} and \texttt{ON DELETE}, \texttt{UNIQUE} constraints that allows only one unique value composition of one or more columns, \texttt{NOT NULL} constraints that rejects \texttt{NULL} value and \texttt{CHECK} constraints. These constraints helps database integrity and prevents invalid records from being stored.

Additionally, database triggers in PostgreSQL are also important for ensuring database integrity of rows that spans over different table records with more complex validation logic. A trigger is automatically executed on a database table operation such as \texttt{INSERT}, \texttt{UPDATE}, or \texttt{DELETE}. If the validation fails for the database trigger, the operation is rejected.

\subsection{Database normalization}

Database normalization is a process to reduce redundancy and avoid data anomalies. The process concerns dividing a large anormal table into smaller tables with relationship between them that complies with the normal form. The main normal forms includes First Normal Form (1NF), Second Normal Form (2NF), and Third Normal Form (3NF).

First Normal Form requires all attributes to contain atomic values, such as \texttt{INT}, \texttt{FLOAT}, \texttt{VARCHAR}, or \texttt{DATE}, and all rows and columns must be unique. Second Normal Form requires First Normal Form and that non-key attributes (attributes that are not a part of candidate key), must depend on the entire candidate key than only a part of it. Third Normal Form specifies that non-key attributes must depend only on the candidate key, along with Second Normal Form, which means that they do not depend transitively on candidate keys.

Database normalization is also another important concept because it helps to avoid unnecessary duplication in the database and makes data maintainance easier, especially in database storage with different types of related information.

\subsection{Conceptual Data Modeling}

Conceptual model shows the high-level system requirements by sketching out the relationship between different entities. The model is independent of specific database management system or implementation. 

Entity-Relationship (ER) modeling can be used for conceptual models. It identifies entities, their attributes, and the relationships between them. Relationships can also have cardinalities, which describes the number of instances of one entity that can be associated with another entity.

Conceptual model is an important initial step because it can visualize, structure and sort out the relationship between different entities from the project description. By translating the project description to an entity-relationship model, the relationships and constraints of the application to be identified before considering the actual database implementation.

\subsection{Logical and Physical Database Design}

Logical database design translates the conceptual model into a relational structure. Entities are represented as tables, attributes become columns, and relationships are implemented using primary and foreign keys. The structure is further refined to satisfy the principles of relational databases but agnostic in terms of database management system.

Physical database design concerns how the logical structure is implemented in a particular database management system. This includes defining data types, constraints, indexes, and other database-specific implementation details.

For this project, a logical-physical diagram is created, which is a combination of logical and physical model. It is a specialized model for simplification in this project, and the model is given in Leif Lindbäck's lecture videos.

The logical-physical database design diagram is ultimately important since it provides the actual database design but with the similar shape as conceptual model.

\subsection{Modelling procedure}

The modelling procedure was accomplished by translating the project requirements and the concept model given in this course, into a conceptual diagram. The translation process started from the given conceptual model and extending it. For each noun in the project description, a candidate entity or attribute was considered, if it hasn't been modeled in the given conceptual model. Every connection between nouns was considered as a candidate relation. Using these approaches,the given conceptual model could then be extended with new entities, for instance study periods, course instances, salary version history, the allocation rule and formulae for derived hours.

After creating the conceptual model, a logical-physical model could be created by extending the conceptual model. This was carried out by following the given steps of the video lecture on logical and physical diagrams.

\begin{enumerate}
  \item For each entity, a table was created for each entity, and the attributes of the entity was assigned as columns.
  \item One-to-one and one-to-many relations were implemented as foreign keys on the side with cardinality one.
  \item Multivalued attributes (many-to-many relations), such as phone numbers, addresses and skills of each employee, were moved to 2 separate tables and connected through cross-reference tables.
  \item A data type was chosen for each column, and \texttt{NOT NULL}, \texttt{UNIQUE} and \texttt{CHECK} constraints were specified to the suitable attributes. This part was accomplished using intuition and by checking the project requirements.
  \item A primary key was chosen for each weak entity, either a generated surrogate key or a composite key of foreign keys. A surrogate key was assigned if the weak entity has a meaning without its affiliated strong entity, a composite key of foreign keys were used. 
  \item For each foreign key, the behaviour on update and delete was decided based on intuition and project requirement, in order to decide which referential integrity action was most suitable for the given case.
  \item The model was checked and evaluated against normal forms up to 3NF, where duplicated and derived data was removed.
  \item Additional rules that cannot be expressed using Astah ER-diagram were instead written as notes/comments, attached to the given property in the diagram.
  \item Finally, the logical-physical diagram was checked that all operations that are mentioned in the project description could be accomplished
\end{enumerate}

After creating the logical-physical diagram, a SQL \texttt{CREATE}-script was verbatimly translated from the logical-physical ER-diagram. Followed by the SQL \texttt{CREATE}-script, the table insertion script and the trigger script were both implemented as well.

\subsubsection{Courses, layouts and instances}

A course is stored in \texttt{course} table with its unique course code and name. Because some attributes of the course might change and needs versioning, such as ECTS credits (hp in the model), minimum and maximum number of students, these are instead stored in \texttt{course\_layout} table. Each course layout is assigned with a version number and \texttt{UNIQUE(course\_id, version)} ensures that each version exists only once per course. When a layout changes, a new row with a higher version number is inserted, while the old one is still kept. Additionally, it is also important that the minimum number of students must be greater than zero while the maximum number must not be smaller than the minimum. Additionally, assigning \texttt{NULL} to maximum number of students means that there is no upper limit, while the minimum possible number of students is 1. A course without any students would therefore be redundant.

The four academic periods, \texttt{P1}, \texttt{P2}, \texttt{P3}, and \texttt{P4} are stored as rows in the lookup table \texttt{period} instead of using \texttt{VARCHAR} or \texttt{ENUM}. The choise is deliberate for leaving space for flexibility. Adding a new academic period or making a period deprecated in large reorganizations could then be supported, while making it still possible for storing historical academic periods.

Additionally, a course instance in \texttt{course\_instance} references exactly one course layout and exactly one academic period. It has a surrogate key, as well as a course instance ID, for example \texttt{2025-50273}. The reason here is that course-instance ID is human-readable and unstable, and the value might be changed. In terms of its attribute, the table stores the number of registered students. Other properties, such as the layout version and the number of ECTS credits could be found using its foreign key \texttt{course\_layout\_id}, since these properties could be considered as inherited. Finally, to prevent same layout being registered twice in the same academic period, the constraint \texttt{UNIQUE(course\_layout\_id, academic\_period\_id)} is used.

\subsubsection{Teaching activities, planned hours and formulae}

The teaching activities are stored as rows in \texttt{teaching\_activity}, which enables insertion of new activities without altering the schema. Teaching activities stored in the table are general and are not affiliated with particular course or course instance. Each activity has a multiplication factor, which indicates the total number of hours for a teacher, including preparation, for each teaching hour. For instance, if the lecture multiplication factor is 3.6, this means that 20 planned lecture hours is equivalent to 72 total hours.

The actual planned hours of each activity in a course instance are stored in the table \texttt{planned\_activity}. With the constraint \texttt{UNIQUE(course\_instance\_id, teaching\_activity\_id)}, an activity could only be planned at most once per instance.

On the other hand, examination and administration hours are derived from the number of students and ECTS credits (hp) and should therefore not be stored anywhere. Instead, the formula of a derived activity are stored in the table \texttt{derived\_activity\_formula}. A sample formula can be viewed as below:
\[
  \textit{hours} = \texttt{base\_hours} + \texttt{hours\_per\_student} \cdot \textit{students} + \texttt{hours\_per\_hp} \cdot \textit{hp}
\]
For examination, the numbers are 32, 0.725 and 0, and for administration they are 28, 0.2 and 2, corresponded to base hours, hours per student respective hours per hp. Each activity has at most one formula, which is ensured by \texttt{UNIQUE} on \texttt{teaching\_activity\_id}. For derived activities, \texttt{planned\_activity.planned\_hours} is \texttt{NULL}, and the hours are calculated by the queries.

\subsubsection{People, employees and departments}

Personal data is stored in \texttt{person}, and employment data in \texttt{employee}. A person is at most one employee, which is ensured by \texttt{UNIQUE} on \texttt{employee.person\_id}. Since a person may have several addresses and phone numbers, and the same address or phone number may be shared by several persons, the relationship is therefore many-to-many. The optional columns \texttt{address\_property} and \texttt{phone\_number\_property} specify the type or property of a given address or phone number. For instance indicating whether a phone number is a home or mobile phone number. The personal number may be \texttt{NULL}, since non-Swedish citizens may not have a Swedish personal number.

Each employee belongs to one department, has one job title from the lookup table \texttt{job\_title}, and has a supervisor, which is another employee. Only the employee at the top of the hierarchy has no supervisor, so \texttt{supervisor\_id} is nullable.

Skills are stored in \texttt{skill} and connected to employees using many-to-many relationship. By storing skills, finding teachers based on skills could be easily carried out.

Each department has exactly one manager, who is also an employee. This creates a circular dependency, since \texttt{department.manager\_employee\_id} references \texttt{employee}, while \texttt{employee.department\_id} references \texttt{department}, and both are \texttt{NOT NULL}. In PostgreSQL, the foreign key of the manager is therefore declared \texttt{DEFERRABLE INITIALLY DEFERRED}. It is checked at the end of the transaction, so that the first departments and their managers can be inserted in the same transaction. In MySQL, which does not support deferrable constraints, the departments are inserted with the foreign key checks temporarily disabled.

Salaries are stored in \texttt{employee\_salary}, one row per salary change. A salary is valid from its \texttt{valid\_from} date until the closest next \texttt{valid\_from} of the same employee. The decision of not storing \texttt{valid\_to} avoids having two salary intervals from overlapping each other. The constraint \texttt{UNIQUE(employee\_id, valid\_from)} prevents two salaries from starting on the same day. Salaries are stored as monthly salaries.

\subsubsection{Allocations and the allocation limit}

Teaching allocations of teachers (employees) are recorded in the table \texttt{teaching\_allocation}, which connects a planned activity of a course instance with an employee and stores the real allocated hours. The hours are stored there as raw hours, whereas the multiplication factor is applied, similar to the expected planned hours. Since the primary key is the combination of primary keys of planned activity and employee, a teacher can be allocated to multiple activities, while an activity can have multiple teachers.

However, the requirement states that a teacher cannot be allocated to more than 4 course instances in each academic period. To enforce the rule, the number 4 is stored in another table \texttt{allocation\_rule.max\_courses}, instead of being hardcoded in the application logic. Since the limit checks multiple rows in different tables, it can not be expressed as a column constraint to the table domain. Instead, the requirement is enforced by the trigger, shown in Listing~\ref{lst:trigger}, which is executed before each insert or update of an allocation. The trigger finds the course instance and the academic period of the new allocation, counts the other course instances that the teacher is already allocated to in the same period, and rejects the allocation if that number is going to exceed \texttt{max\_courses}.

\begin{lstlisting}[style=sql, caption={*** The trigger that enforces the maximum number of course instances per teacher and period (\texttt{trigger-postgresql.sql}). ***}, label={lst:trigger}]
CREATE OR REPLACE FUNCTION validate_4_instances_each_study_period()
RETURNS TRIGGER AS $$
DECLARE
    new_instance_id INTEGER;
    new_academic_period_id INTEGER;
    current_value INTEGER;
    max_value INTEGER;
BEGIN
    -- extract instance_id and academic_period_id
    SELECT course_instance.id, course_instance.academic_period_id
    INTO new_instance_id, new_academic_period_id
    FROM planned_activity
    INNER JOIN course_instance ON course_instance.id = planned_activity.course_instance_id
    WHERE planned_activity.id = NEW.planned_activity_id;

    -- count the number of teaching_allocation from given employee and academic period
    SELECT COUNT(DISTINCT course_instance.id)
    INTO current_value
    FROM teaching_allocation
    INNER JOIN planned_activity ON planned_activity.id = teaching_allocation.planned_activity_id
    INNER JOIN course_instance ON course_instance.id = planned_activity.course_instance_id
    WHERE teaching_allocation.employee_id = NEW.employee_id
      AND course_instance.academic_period_id = new_academic_period_id
      AND course_instance.id <> new_instance_id;

    SELECT max_courses
    INTO max_value
    FROM allocation_rule
    ORDER BY id
    LIMIT 1;

    IF current_value >= max_value THEN
        RAISE EXCEPTION 'Problem: A teacher cannot be assigned to more than % course instances each academic period. Employee id: %, already allocated: %', max_value, NEW.employee_id, current_value;
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE OR REPLACE TRIGGER trigger_4_instances_each_study_period
BEFORE INSERT OR UPDATE
ON teaching_allocation
FOR EACH ROW
EXECUTE FUNCTION validate_4_instances_each_study_period();
\end{lstlisting}

\subsection{Insertion of sample data}

\subsection{Comparison between requirement and result}

The project requirements are met by the tables and table properties below:

The course layout requirement, including course code, name, ECTS credits, minimum and maximum number of students, is met through the \texttt{course} and \texttt{course\_layout} tables. Furthermore, the course instance requirement, including ID, period, year, and number of students, is met through the \texttt{course\_instance}, \texttt{academic\_period}, and \texttt{period} tables.

Additionally, teaching activities can be extended and support multiplication factors through rows in the \texttt{teaching\_activity} table. Planned hours, as well as derived examination and administration hours, are handled through the \texttt{planned\_activity} and \texttt{derived\_activity\_formula} tables.

In terms of department-to-employee relationship, each department has a manager, who must also be an employee of the organisation. This relationship is implemented through the \texttt{department.manager\_employee\_id} attribute, which references the corresponding employee.

Employee information, including department affiliation, contact details, salary, job title, skills, and supervisor, is distributed across several related tables. The main information is stored in \texttt{employee} and \texttt{person}, while additional details are handled by \texttt{person\_address}, \texttt{person\_phone\_number}, \texttt{employee\_salary}, \texttt{job\_title}, and \texttt{employee\_skill}. The \texttt{supervisor\_id} attribute identifies an employee's supervisor.

Putting it together, the many-to-many relationship between teachers and course instances is implemented through the \texttt{teaching\_allocation} table. This allows multiple teachers to be assigned to the same course instance, while also allowing each teacher to participate in multiple course instances. The restriction that a teacher may be assigned to a maximum of four course instances during a given period is enforced through \texttt{allocation\_rule.max\_courses} and the database trigger presented in Listing~\ref{lst:trigger}.

For the higher-grade requirement, all relevant data must be stored in the database is fulfilled by storing limits, multiplication factors, formula constants, and period dates as data rather than hardcoding these values into the application logic. These are fulfilled since none of the data is stored in the application logic or left for application data to process.

Finally, the higher-grade requirement that course layouts and salaries must be changeable over time is supported through versioning in \texttt{course\_layout.version} and salary history maintained in \texttt{employee\_salary}. This makes it possible to preserve previous versions of course layouts and historical salary information when changes occur.
